# راهنمای تداوم پروژهٔ صبابار

**آخرین مرور کد:** ۱۵ نوامبر ۲۰۲۶
**هدف سند:** نگه‌داشتن تصویر مشترک از هدف محصول، امکانات فعلی، قواعد کسب‌وکار و نیازهای استقرار؛ تا توسعه‌های بعدی روی رفتار موجود سوار شوند.

> این سند از کد و تنظیمات همین شاخهٔ کاری تهیه شده است. هنگام تهیه، چند فایل پروژه تغییر ثبت‌نشده داشتند؛ پیش از تغییر یا انتشار، `git status` و تفاوت کد با نسخهٔ منتشرشده را بررسی کنید. این راهنما به‌تنهایی تأیید نمی‌کند که سرور اصلی همین نسخه را اجرا می‌کند.

## ۱. هدف و مرز محصول

صبابار یک سامانهٔ داخلی برای ثبت پروندهٔ راننده و پیگیری فرایند فروش اعتباری کالا است. هر راننده یک پرونده دارد که اطلاعات، کالاها، پیش‌نویس مرحله‌ها، مدارک، پرداخت‌ها و تاریخچهٔ رویدادهایش در آن نگهداری می‌شود.

سامانه در وضعیت فعلی مستقل از ERP، پنل فروشگاه و سرویس پیامک یا تأمین اعتبار بیرونی است. فرایندها و مبلغ‌ها از پنل توسط کاربر وارد یا تأیید می‌شوند. بنابراین «تسویه با تأمین‌کننده» از روی ERP خوانده نمی‌شود و مبلغ بدهی آن را کاربر مالی تعیین می‌کند.

نشانی اصلی که در گفت‌وگو برای محیط عملیاتی داده شده: `https://sabadashboard.liara.run/`. پیش از هر تغییر روی محیط اصلی، وضعیت انتشار و داده‌های واقعی باید جداگانه کنترل شوند.

## ۲. فناوری و چیدمان کد

| مسیر | مسئولیت |
| --- | --- |
| `web/` | پنل React 18 و TypeScript، ساخته‌شده با Vite؛ نمایش فارسی و راست‌چین |
| `api/` | API با NestJS؛ احراز هویت، مجوزها، گردش پرونده، فایل‌ها و تراکنش‌ها |
| `api/prisma/` | مدل PostgreSQL و مهاجرت‌های نسخه‌بندی‌شده |
| `docs/` | راهنمای استقرار و مستندات پروژه/آزمون |
| `scripts/` | ابزارهای smoke test محلی و ساخت فایل آزمون |
| `liara.json` | تنظیمات پایهٔ Liara: پورت ۳۰۰۱، منطقهٔ ساخت ایران، بدون دیسک متصل |
| `render.yaml` | Blueprint محیط آزمایشی Render؛ تنظیمات و منابع آن را با محیط اصلی یکی فرض نکنید |

در production، NestJS فایل‌های ساخته‌شدهٔ `web/dist` را سرو می‌کند؛ API زیر پیشوند `/api` است و مسیرهای دیگر به صفحهٔ React برمی‌گردند. برای میزبانی معمول، یک سرویس Node و یک PostgreSQL پایدار لازم است؛ وب و API جداگانه لازم نیستند.

نسخهٔ راهنمای اجرای محلی در `README.md` نام Node.js 24، npm و PostgreSQL 16 را می‌دهد. خود `docker-compose.yml` پورت PostgreSQL را روی `127.0.0.1:5433` منتشر می‌کند؛ دیتابیس آمادهٔ همین رایانه در README روی `127.0.0.1:5434` است. این دو تنظیم را با هم اشتباه نگیرید.

## ۳. ماژول‌ها و کاربردشان

### احراز هویت و دسترسی‌ها

- راه‌اندازی اولیه، ورود، خروج و دریافت کاربر جاری در `api/src/auth/`.
- نشست در کوکی `HttpOnly` و در production با `Secure` ذخیره می‌شود؛ توکن نشست خام در دیتابیس نیست و hash آن ذخیره می‌شود.
- ساخت اولین مدیر با `BOOTSTRAP_TOKEN` و فقط وقتی هنوز کاربری ثبت نشده ممکن است. رمز پیش‌فرضی در مخزن تعریف نشده است.
- `RolesGuard`، `AuthGuard` و `CsrfGuard` در `api/src/common/` محافظت سراسری/مسیرها را انجام می‌دهند. درخواست تغییردهنده باید `Origin` برابر `APP_ORIGIN` باشد.

### پرونده و گردش فروش

- فهرست، جست‌وجو، شمارندهٔ مرحله، پیش‌نویس، اقدام، آرشیو و بازگردانی در `api/src/drivers/`.
- مرحله‌ها به‌ترتیب:
  1. اعلام تمایل
  2. ثبت‌نام و احراز هویت در اپ
  3. اعتبارسنجی
  4. پیش‌فاکتور، پرداخت و رزرو
  5. قرارداد و چک
  6. تحویل و مستندات نهایی
  7. تکمیل‌شده
- اطلاعات فرم هر مرحله جداگانه به‌عنوان پیش‌نویس سروری ذخیره می‌شود؛ ذخیرهٔ پیش‌نویس به‌تنهایی مرحله را جلو نمی‌برد. اقدام نهایی مرحله، دسترسی و داده‌های الزامی را بررسی می‌کند و رویداد تاریخچه می‌سازد.
- تأیید اعتبار به نقش «تأیید اعتبار» سپرده شده؛ ثبت و تأیید پرداخت اولیه و بررسی قرارداد/چک نیازمند نقش مالی است. فروش و عملیات بیشتر اقدام‌های ثبت و تحویل را انجام می‌دهد. سوپرادمین دسترسی مدیریتی دارد.
- تکمیل تحویل به ثبت تاریخ تحویل و تأییدهای فیزیکی قرارداد، چک و تحویل کالا نیاز دارد. ویدئوی رضایت راننده برای تکمیل الزامی نیست.
- پروندهٔ آرشیوشده از گردش فعال کنار می‌رود و مرحلهٔ فعلی‌اش حفظ می‌شود. آرشیوکردن برای فروش و عملیات و بازگرداندن از آرشیو فقط برای سوپرادمین مجاز است. تاریخچه و داده‌ها با آرشیو حذف نمی‌شوند.
- صفحهٔ گردش فروش، مرحلهٔ «همهٔ مراحل» و فهرست مرحلهٔ «تکمیل‌شده» دارد. پیش‌فرض صفحهٔ گردش روی «اعلام تمایل» است.

### مدارک

- مدارک خصوصی‌اند و دانلود از مسیر احراز هویت‌شدهٔ API انجام می‌شود؛ مسیر فایل داخل پوشهٔ عمومی وب نیست.
- کد فعلی PDF، JPG/JPEG، PNG، WebP و MP4 را می‌پذیرد و امضای اولیهٔ فایل را هم بررسی می‌کند. حداکثر پیش‌فرض فایل عادی ۲۰ مگابایت و ویدئو ۱۵۰ مگابایت است.
- آپلودها و حذف مدرک در تاریخچه ثبت می‌شوند. ویدئوی رضایت اختیاری است.
- پیاده‌سازی فعلی نوشتن فایل production را در Liara Object Storage انجام می‌دهد. فایل‌های Supabase فقط برای خواندن فایل‌های قدیمی نگه داشته شده‌اند.

### کالا و تسویه با تأمین‌کنندگان

- صفحهٔ «تسویه با تأمین‌کنندگان» ماژول `web/src/SupplierSettlementsPage.tsx` و API `api/src/supplier-settlements/` دارد؛ دسترسی آن برای نقش حقوقی و مالی و سوپرادمین است.
- ردیف کالا از کالای ثبت‌شده در پیش‌فاکتور پرونده می‌آید. برای پرونده‌های قدیمیِ تکمیل‌شده، مهاجرت `20261114120000_backfill_completed_driver_products` سطر کالا را از پیش‌نویس پیش‌فاکتور به `DriverProduct` منتقل می‌کند؛ قبل از اجرای مهاجرت روی دیتابیس عملیاتی، بکاپ لازم است.
- پرونده‌های مرحلهٔ تحویل و تکمیل‌شده برای این فهرست واجد شرایط‌اند. در صورت ثبت‌نشدن کالای لازم، نقش مالی می‌تواند قلم خرید را از فهرست خرید اضافه و عنوان، تعداد و قیمت فروش را ویرایش کند.
- جمع مبلغ فروش از تعداد × قیمت واحد فروش محاسبه می‌شود. مبلغ بدهی به تأمین‌کننده از مبلغ فروش حدس زده نمی‌شود: بار اول باید مبلغ کل بدهی و فروشگاه مشخص شود و بعداً قابل ویرایش است.
- پرداخت به تأمین‌کننده به‌صورت چند رکورد با مبلغ و تاریخ ثبت می‌شود؛ پرداخت‌شده جمع رکوردها و مانده برابر بدهی کل منهای پرداخت‌ها است. انتخاب‌های فعلی فروشگاه در کد: «فروشگاه هایپر تایرایران» و «فروشگاه معدن تایر شرق».
- گزارش‌های تجمیعی این بخش در محدودهٔ فعلی نیستند. گزارش رویدادهای مدیریتی، ماژول جداگانه‌ای است و جای گزارش مالی کالاها را نمی‌گیرد.
- «تسویهٔ فروشگاه» داخل پرونده و «تسویه با تأمین‌کنندگان» دو مفهوم و دو مدل دادهٔ مستقل‌اند (`StoreSettlement` در برابر `SupplierSettlementRecord`). هنگام توسعه این دو را یکی فرض نکنید.

### کاربران و گزارش رویدادها

- مدیریت کاربران و نقش‌ها فقط برای سوپرادمین نمایش داده می‌شود.
- گزارش رویدادها تغییرات مهم پرونده، مدارک، آرشیو و عملیات مالی را از `AuditEvent` می‌خواند.

## ۴. نقش‌ها

نقش‌های تعریف‌شده در `web/src/model.ts` و Prisma:

| نقش | مسئولیت اصلی |
| --- | --- |
| `SUPER_ADMIN` | مدیریت کاربران، مشاهدهٔ همهٔ بخش‌های مدیریتی و بازگرداندن پرونده از آرشیو |
| `SALES_OPERATIONS` | ثبت متقاضی، پیش‌نویس‌ها و اقدامات فروش/تحویل؛ آرشیو پرونده |
| `CREDIT_APPROVER` | تصمیم‌های اعتبارسنجی |
| `LEGAL_FINANCE` | تأییدهای مالی/حقوقی، پرداخت و تسویهٔ کالاها |

قفل یا پنهان‌کردن دکمه در رابط کاربری، جای مجوز API را نمی‌گیرد؛ هر اقدام حساس باید در سرویس API هم مجوز نقش داشته باشد.

## ۵. مدل دادهٔ اصلی

- `User`, `Session`: کاربران، نقش‌ها و نشست‌ها.
- `Driver`: هویت راننده، مرحله/وضعیت جاری و اطلاعات آرشیو.
- `StageDraft`: آخرین پیش‌نویس هر مرحله برای هر پرونده.
- `DriverDocument`: فرادادهٔ فایل و کلید فضای ذخیره‌سازی؛ خود فایل در object storage است.
- `DriverProduct`: عنوان، تعداد، قیمت فروش، و در صورت وجود بهای تأمین کالا.
- `SupplierSettlementRecord`: snapshot عنوان/تعداد/قیمت و بدهی کل، نام فروشگاه و یک پرداخت ثبت‌شده. چند پرداخت برای یک قلم کالا از طریق چند ردیف ذخیره می‌شود.
- `StoreSettlement`: تسویهٔ مستقل فروشگاه در پرونده.
- `DriverInstallment`: جدول اقساط راننده که در migration و API باقی مانده است؛ به بخش نکات/ابهام‌های فعلی توجه کنید.
- `AuditEvent`: رویداد و جزئیات JSON آن.

مهاجرت‌های SQL زیر `api/prisma/migrations/` مرجع تغییر schema هستند. در production از `prisma migrate deploy` استفاده کنید، نه `prisma migrate dev`.

## ۶. نکتهٔ مهم پیش از ادامهٔ توسعه: اقساط راننده

در گفت‌وگو تصمیم گرفته شد بخش اقساطی که به شکل قبلی در پرونده ساخته شده بود فعلاً حذف/کنار گذاشته شود. با این حال، در وضعیت فعلی مخزن هنوز مدل `DriverInstallment`، APIهای اقساط، بخشی از متن تاریخچه و تولید خودکار برنامهٔ اقساط هنگام `CONFIRM_INITIAL_PAYMENT` وجود دارد. رابط اصلی فهرست، ماژول مستقل اقساط ندارد.

پس این قابلیت را «ویژگی نهایی و مورد تأیید» فرض نکنید یا روی آن توسعه نسازید. پیش از اضافه‌کردن بخش‌های جدید مالی، باید با صاحب محصول تعیین شود این کد قدیمی صرفاً بی‌استفاده است یا باید از مسیر پرداخت/API و migrationهای بعدی هم حذف شود. این مستند عمداً تفاوت تصمیم محصول با کد باقی‌مانده را ثبت می‌کند.

## ۷. اجرای محلی

### دیتابیس Docker

از پوشهٔ ریشه:

```sh
npm ci
```

یک `.env` ریشه از روی `.env.example` بسازید، `POSTGRES_PASSWORD` محلی تعیین کنید، سپس:

```sh
npm run db:up
npm run db:generate
npm run db:migrate
npm run dev:api
```

در ترمینال دوم:

```sh
npm run dev:web
```

رابط توسعه در `http://127.0.0.1:5174` و API در پورت ۳۰۰۱ اجرا می‌شود. پورت دیتابیس Docker برابر ۵۴۳۳ است.

### دستورات رایج

| فرمان | کار |
| --- | --- |
| `npm run build` | تولید Prisma Client و ساخت API و وب |
| `npm run build:api` | ساخت API |
| `npm run build:web` | type-check و ساخت Vite |
| `npm run db:generate` | تولید Prisma Client |
| `npm run db:migrate` | مهاجرت توسعه‌ای؛ فقط محیط توسعه |
| `npm run db:migrate:deploy` | اجرای migrationهای ازقبل‌ساخته‌شده |
| `npm run test:unit` | آزمون واحد API و وب |
| `npm run test:smoke` | smoke test انتها‌به‌انتها؛ فقط loopback و حساب آزمون محلی |

Smoke test دادهٔ موقت می‌سازد و خودش را پاک/آرشیو می‌کند؛ طبق راهنمای `docs/test-plans/README.md` از production پشتیبانی نمی‌کند. آن را به محیط اصلی اشاره ندهید.

## ۸. استقرار روی سرور تازه

### منابع لازم

1. سرویس Node.js 24 با دسترسی خروجی به دیتابیس و object storage.
2. PostgreSQL پایدار (ترجیحاً مدیریت‌شده)، با بکاپ زمان‌بندی‌شده و بازیابی آزمایش‌شده.
3. Liara Object Storage با bucket خصوصی برای فایل‌ها؛ فضای دیسک موقت برنامه را برای اسناد استفاده نکنید.
4. دامنه و HTTPS؛ `APP_ORIGIN` باید دقیقاً origin مرورگر باشد (scheme و hostname، بدون path و slash انتهایی).
5. متغیرهای محیطی زیر در تنظیمات محرمانهٔ سرویس؛ نه در Git، image، frontend یا log.

### متغیرهای محیطی

| نام | نیاز | کاربرد |
| --- | --- | --- |
| `NODE_ENV` | لازم در سرویس اصلی | مقدار `production`؛ فعال‌کردن cookie امن و سرو فایل وب |
| `DATABASE_URL` | لازم | اتصال PostgreSQL که از برنامه قابل دسترس باشد |
| `APP_ORIGIN` | لازم | origin دقیق وب؛ برای CORS و کنترل Origin درخواست‌های تغییردهنده |
| `BOOTSTRAP_TOKEN` | لازم فقط برای راه‌اندازی اولیه | مقدار تصادفی امن حداقل ۳۲ نویسه برای ساخت سوپرادمین اول |
| `PORT` | معمولاً توسط میزبان | پورت برنامه؛ پیش‌فرض کد ۳۰۰۱ است و `liara.json` نیز ۳۰۰۱ اعلام می‌کند |
| `HOST` | اختیاری | در production پیش‌فرض `0.0.0.0` است |
| `SESSION_TTL_HOURS` | اختیاری | عمر نشست، پیش‌فرض ۱۲ ساعت و محدودشده به ۱ تا ۲۴ ساعت |
| `LIARA_ENDPOINT` | لازم برای آپلود production | endpoint HTTPS فضای Liara، بدون credential/query/fragment |
| `LIARA_BUCKET_NAME` | لازم برای آپلود production | نام bucket خصوصی |
| `LIARA_ACCESS_KEY` | لازم برای آپلود production | کلید دسترسی فقط‌سرور با حداقل مجوز لازم |
| `LIARA_SECRET_KEY` | لازم برای آپلود production | secret فقط‌سرور؛ هرگز در مستند عمومی یا مخزن ننویسید |
| `MAX_DOCUMENT_BYTES` | اختیاری | سقف فایل عادی، پیش‌فرض ۲۰٬۹۷۱٬۵۲۰ بایت |
| `MAX_VIDEO_BYTES` | اختیاری | سقف ویدئو، پیش‌فرض ۱۵۷٬۲۸۶٬۴۰۰ بایت |
| `SUPABASE_URL`, `SUPABASE_STORAGE_BUCKET`, `SUPABASE_SERVICE_ROLE_KEY` | فقط برای خواندن فایل‌های قدیمی Supabase | دسترسی محرمانهٔ server-side؛ برای آپلود جدید در پیاده‌سازی فعلی جای Liara را نمی‌گیرد |
| `FILE_STORAGE_DIR` | توسعه/آزمون محلی | ذخیرهٔ محلی؛ برای production بدون دیسک پایدار استفاده نشود |

نام و مقدار محرمانهٔ واقعی کلیدها باید فقط از پنل امن provider در اختیار مدیر استقرار باشد. هیچ‌کدام را در فایل راهنمای عمومی، issue یا خروجی build ثبت نکنید.

### فرمان‌های ساخت و شروع

Root scriptها در `package.json` این ترتیب را پشتیبانی می‌کنند:

```sh
npm ci
npm run build
npm start
```

`npm run build`، Prisma Client و هر دو پروژهٔ وب/API را می‌سازد. `npm start` ابتدا `prisma migrate deploy` و سپس API production را اجرا می‌کند. در داشبورد میزبان یا pipeline، معادل این دو فرمان را به‌عنوان build و start command تنظیم کنید. پورت سرویس را با پورت اعلام‌شده به میزبان هماهنگ کنید.

در Liara، `liara.json` فعلی پورت ۳۰۰۱ و منطقهٔ build ایران را دارد اما build/start command، متغیرهای محیطی و دیسک پایدار را کامل تعریف نمی‌کند (`disks` خالی است). برای همین تنظیمات نهایی داشبورد و Object Storage ضروری‌اند. `render.yaml` یک مسیر staging جدا با مقادیر محیطی Supabase دارد؛ آن را نسخهٔ production یا تنظیم جاری Liara فرض نکنید. نمونه‌های `.env.example` و `api/.env.example` الگو هستند و secret واقعی نیستند.

### راه‌اندازی و انتشار امن

1. ابتدا PostgreSQL و bucket خصوصی را بسازید؛ اتصال شبکه و مجوز دسترسی را به سرویس API محدود کنید.
2. بکاپ قابل‌بازیابی از دیتابیس قدیمی بگیرید، اگر قرار است داده منتقل شود. فایل‌ها را هم با حفظ mapping `storageKey` منتقل یا دسترسی فقط‌خواندنی به محل قدیمی‌شان نگه دارید.
3. تنظیمات محرمانه را در پنل سرور ثبت کنید. `APP_ORIGIN` را دقیقاً مطابق نشانی HTTPS کاربر قرار دهید.
4. build بسازید؛ پیش از migration روی production از snapshot/back-up تازه مطمئن شوید. migrationهای برنامه هنگام start با `prisma migrate deploy` اجرا می‌شوند.
5. health/readiness را از `GET /api/auth/setup-status` بررسی کنید. این endpoint وضعیت راه‌اندازی را می‌دهد و وجود اولین کاربر را گزارش می‌کند.
6. در ورود نخست، با `BOOTSTRAP_TOKEN` سوپرادمین را از صفحهٔ راه‌اندازی بسازید؛ سپس توکن راه‌اندازی را از تنظیمات سرویس حذف/تعویض کنید.
7. حساب‌های واقعی را بسازید و نقش‌ها را با مسئول سامانه تطبیق دهید. دسترسی سوپرادمین را محدود کنید.
8. با حساب‌های مجاز، ورود/خروج، فهرست‌ها، پیش‌نویس، یک گذار گردش، دانلود مدرک، آپلود در bucket، آرشیو/بازگردانی و ثبت/نمایش تسویه را در staging بررسی کنید.
9. لاگ‌های API، خطاهای اتصال DB/object storage، ظرفیت bucket، بکاپ و هشدارهای downtime را پایش کنید. پس از انتشار، بازیابی بکاپ را در محیط جداگانه هم تمرین کنید.

اگر دادهٔ موجود به سامانهٔ تازه منتقل می‌شود، migrationهای schema جایگزین برنامهٔ انتقال داده و فایل نیستند. ابتدا migration و backfill را روی نسخهٔ کپی‌شدهٔ دیتابیس تمرین و نتیجه را با شمارش/نمونه‌برداری تطبیق دهید.

## ۹. وضعیت فعلی و موارد باز برای ادامه

- پنل پرونده، مدارک خصوصی، آرشیو و گردش فروش وجود دارد.
- ثبت کالا با پیش‌فاکتور و فهرست تسویهٔ تأمین‌کننده فعال است؛ بدهی تأمین‌کننده باید دستی مشخص شود.
- کاربر درخواست کرده گزارش‌های مالی/تجمیعی تسویه فعلاً کنار گذاشته شوند.
- ویدئوی رضایت در تحویل اختیاری است.
- روی فهرست آرشیو دکمهٔ بازگردانی وجود دارد؛ API آن را فقط برای سوپرادمین مجاز می‌کند.
- ستون «آخرین تغییر» از فهرست رانندگان حذف شده تا ستون اقدام فضای بیشتری بگیرد؛ زمان و جزئیات رویدادها در تاریخچهٔ پرونده/گزارش رویدادها بماند.
- اقساط راننده موضوع تصمیم‌گیری است و هنوز بقایای اجرایی در API/database دارد؛ قبل از تغییر مالی بعدی این ابهام را تعیین تکلیف کنید.
- اتصال ERP، فروشگاه، درگاه پرداخت، پیامک، گزارش دیرکرد و گزارش‌ساز تسویه در محدودهٔ فعلی پیاده‌سازی نشده‌اند.
- پیش از انتشار کد جدید، فهرست و وضعیت migration دیتابیس، سازگاری فایل‌های قدیمی، مجوزها و صحت پشتیبان‌گیری بررسی شوند.
